# Astro 7 factory assessment (Issue #55)

**Date:** 2026-09-23

**Scope:** research only; no dependency, template, runtime or rollout change.

## Observed baseline

- `templates/base-astro/package.json` declares Astro `^5.5.0`, `@astrojs/tailwind` `^6.0.0`, Tailwind `^3.4.17`, Keystatic Astro `^5.0.0`, Node adapter `^9.0.0`, Markdoc `^0.15.0`, and Zod `^3.24.0`.
- A disposable site generated by the supported `scripts/create-site.mjs` command passed `npm ci`, `npm run verify`, and `npm run build` on 2026-09-23 (local public static profile, Node 24). No factory-specific failure requiring Astro 7 was observed in that run; editor-host authorization and production behavior were not tested.
- The separate consumer's [PR #31](https://github.com/ozand/site-ayga/pull/31) reports a successful local Astro 7.3 migration with Tailwind 4/Vite plugin and separate static/editor profiles. This establishes a single consumer's bounded result, not factory compatibility.

## Compatibility evidence and limits

Read-only registry queries (reproduce with `npm view <package>@<version> peerDependencies --json` and `npm view astro@7.3.3 engines --json`):

| Package | Observed metadata | Implication |
| --- | --- | --- |
| `@astrojs/tailwind@6.0.2` | Astro `^3 || ^4 || ^5`; Tailwind `^3.0.24` | Existing integration does not advertise Astro 7 compatibility; a new styling path must be evaluated. |
| `@astrojs/markdoc@0.15.0` / `@2.0.9` | Astro `^5` / `^7` respectively | Template Markdoc line would need a compatibility update. |
| `@astrojs/node@9.0.0` / `@11.1.6` | Astro `^5` / `^7.2.1` respectively | Private editor adapter would need a matching version and its own build checks. |
| `@keystatic/astro@6.0.0` | Astro `5 || 6 || 7`, React `^18.2 || ^19` | Candidate integration exists; no factory editor/auth test performed. |
| `astro@7.3.3` | Node `>=22.12.0`, npm `>=9.6.5` | Upgrade would raise the required toolchain floor. |

Registry metadata is a compatibility signal, not proof that a migrated scaffold works. Tailwind 4, shadcn components, schemas, static artifact exclusion and editor behavior remain untested **in the factory**. No claim is made that all shadcn installations are incompatible or that one replacement styling integration is the only possible solution.

## Alternatives and decision

- **Migrate the factory now:** rejected for this research increment. It changes dependency/toolchain contracts and requires an ADR, owner approval and full clean-scaffold verification; the consumer result does not substitute for those checks.
- **Retain Astro 5 for now:** recommended. The current disposable public scaffold passed; no reproducible factory-specific Astro 7 need has been established by this bounded research.
- **Defer until a concrete constraint arises:** retain as the reconsideration trigger. A documented incompatibility, supported baseline deadline or approved new requirement would justify a separate migration decision.

The two-working-day research timebox was not exhausted; the early abandon condition is met: no reproducible factory-specific need was observed. **Do not open a migration implementation under this Issue.** This does not establish future Astro 5 support duration, security status, or production readiness. Before any migration: record a Proposed ADR for the dependency/public contract, obtain explicit owner approval, then scaffold a disposable site and run `npm install`, `npm run verify`, `npm run build`, `npm run build:editor`, plus static-artifact editor exclusion and authorized editor-profile smoke checks. No such migration was performed here.
